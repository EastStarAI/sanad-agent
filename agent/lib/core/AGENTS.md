# Agent Core Contract

## Scope
This contract applies to `agent/lib/core/`.

## Core Ownership
- Own configuration, environment paths, identity/auth persistence, provider runtime, shared request/message models, and dependency-composition primitives.
- `core/update/` owns verified standalone-agent replacement. CLI, local daemon, and client requests must delegate to it; source/FVM execution must never pull Git or replace a checkout.
- `core/setup/` owns typed service state, platform capability selection, service-definition generation, lifecycle execution, ownership metadata, conflict migration, and transactional restore; entry points only validate commands and present results.
- Do not absorb engine loops, interface protocols, capability catalogs, or evolution database workflows.
- Keep shared models transport-neutral and JSON-safe where they cross persistence or protocol boundaries.

## Environment and Identity
- Resolve runtime environment from process variables before the global `SANAD_HOME` environment file.
- Load non-secret context-window and compaction policy from `SANAD_HOME/config.yaml` once at daemon startup; provider credentials and other secrets never belong there.
- A Dart test must explicitly select temporary state or inject an in-memory/explicit-path database before opening agent state; inherited `SANAD_HOME` is never test isolation.
- `AuthManager` owns persistent `hardware_id`; create it locally when absent and keep it distinct from backend-assigned device ids.
- Persist non-secret Sanad auth metadata and temporary pairing state in `SANAD_HOME/auth.json` with owner-only Unix permissions or equivalent Windows ACL. Agent P-256 private keys and durable Device Credentials belong only in the OS-backed Agent secret store and must never be rewritten to JSON.
- A UI-issued device token is initial pairing authority only. Before the first
  cloud registration, generate and vault-persist a distinct durable Device
  Credential plus an Agent P-256 key. Claim sends pairing authority, public JWK,
  and a fresh Gateway nonce proof; Backend atomically binds the credential to
  that thumbprint. Remove pairing/pending state only after `register_success`.
  Lost-response retry reuses the same credential/key with a fresh nonce proof.
- Refresh `sanad_client` User access through the Portal lifecycle, send refresh tokens in request bodies, and never log raw credentials. A User session does not make the Agent cloud-ready. For automatic co-located sign-in, the Agent starts a non-authorizing key-bound enrollment with its non-secret persistent hardware identity, exposes only the request identity locally, and redeems the Device Credential itself with proof of possession. Default enrollment display names use `Sanad Agent (<OS name>)`, never hostnames or IP addresses. Headless Agent login instead owns the same P-256 identity and stores only a key-bound `sanad_agent` Device Credential; it never receives a User refresh token.
- Persist Agent private keys and durable credentials through the platform store abstraction: macOS Keychain, Windows DPAPI-protected ciphertext, or Linux capability-selected Secret Service/owner-protected storage. Linux probes Secret Service with a synthetic write/read/delete, persists one backend identity, and otherwise uses the atomic owner-only Sanad Home file backend without claiming encryption. A selected backend never reads stale credentials from another backend; migration to Secret Service deletes owner-file bytes only after every write/read verification succeeds. Legacy files are removed only after verified migration. Provider credentials, MCP secrets and user secrets use the same store through `SecretVaults` (`providers:`/`mcp:`/`custom:` namespaces; `custom:` has no plaintext predecessor and is never written to a file, verified writes, per-owner index, cross-process lock and generation marker); the daemon, and a CLI command that can read or write a secret, open it at startup, which migrates and then deletes `provider_secrets.json` and `mcp_secrets.json`. A failed migration leaves those files in place. Who may start a macOS Keychain authorization dialog is a per-process decision (`SecretVaultPolicy`): the daemon and an interactive CLI keep it, a process with no person present forbids it, and only then is interaction suppressed (per query through `kSecUseAuthenticationContext`, plus the legacy file-keychain switch). An authorization-demanding item therefore either prompts the person who is there, or closes the vault with a reason-coded `AgentSecretStoreUnavailable` that the daemon log, `sanad doctor`, and the gateway `/health` payload report; it never blocks an unattended process. A process that never opened the vault cannot mutate a plaintext secret store. Vault lifecycle events go through the owner-only `secret_vault_events.jsonl`, and the daemon replays them into the agent log after logging starts; never log secret values there. Device code, pairing authority, pending credentials, and proof JWTs never enter `auth.json`, URLs, Agent CLI arguments, or logs. Replacement pairing snapshots a prior Device Credential only in the selected secret backend; cancellation restores it atomically, while authoritative registration discards the snapshot.
- Every native `auth.json` mutation participates in the shared `auth.refresh.lock` transaction. Refresh must acquire the lock before re-reading credentials and must adopt a pair rotated by another process instead of submitting the old refresh credential again.
- `AuthManager` publishes a credential-free process-local change signal only after a successful auth write or a meaningful external reload; credentials never enter that signal.
- Desktop logout intent is non-secret shared auth metadata. `AuthManager` consumes it under `auth.refresh.lock` before cloud authorization, verifies deletion of durable and pending Agent credentials, clears stale pairing state, and preserves `hardware_id` plus any newer Client session. A later Client login never authorizes reuse of a prior account's Agent credential.
- Provider credentials must never share Sanad identity storage.

## Provider Runtime
- `ProviderRegistry` is the source of supported provider templates; `ProviderInstance` UUID is routing identity and display name is presentation metadata.
- A model's dispatch wire is resolved once in `AgentRuntimeService.resolveSignature` and frozen into `RouteSignature` (`protocol`, `normalizedBaseUrl`, additive `apiMode`, persisted as compaction `api_mode`). Per-model catalog wires come only from `ProviderModelWire` for `catalogModelWire` templates (Task 120); thinking authority sees the same wire through the transient `ThinkingCapabilityAssembler.routeInstance` view, which is never persisted.
- `core/provider_usage/` owns the unified account-usage models, per-template usage adapters, and the usage adapter registry (Task 55). The registry is the single authority for whether an instance supports usage queries; clients must not hardcode a provider list. Adapters are auth-method-independent and read-only in v1; ChatGPT (`openai-codex`) maps `primary_window`/`secondary_window` to Session/Weekly and never synthesises a placeholder. Snapshots never carry credentials, account ids, or raw provider payloads.
- `core/provider_thinking/` owns typed thinking-control descriptors, native directive unions, the layered capability authority, provider-reported policies, and the thinking policy registry (Task 43). Adapters own wire payloads and must not infer capability from `supportsReasoning` alone.
- Thinking capability authority has five layers; the first layer with a `thinking_control` record for the exact model id wins as a whole, with no field mixing: (1) user settings — `model_capabilities` in `$SANAD_HOME/config.yaml`, exact model id, no wildcards or provider scoping; (2) provider-reported `/models` metadata for the exact route — endpoint `thinking_control` declarations from provider-owned discovery parsers (OpenRouter, LM Studio, Kimi) and native item schemas (Codex `supported_reasoning_levels`, the Ollama live probe); (3) shipped defaults generated from `agent/model_capability_defaults.yaml` (same schema, a documentation `source` per entry, applied by route class); (4) the serving vendor's exact `ModelsDevService` entry; (5) the models.dev entry named by that entry's `canonical_model_id`, only when layer 4 reports no `reasoning_options`. Otherwise the route is `unknown`. The single exception to whole-record winning is the default fill: when the winning record has options but no default, the default comes from the next layer in precedence order (skipping the winner) that declares one for the same exact model id — the shipped record regardless of its route class, then the models.dev serving entry, then its canonical entry — only when it is one of the winning options; options never come from another layer, a winning shipped record never donates to itself, and the descriptor records `default_source`. Model names never appear in Dart capability logic; they live only in the shipped-defaults data.
- An `unknown` route admits the turn with the provider default and no thinking field; the selection passes through unchanged. A route with a reported set clamps an unoffered selection to the nearest lower supported level, never escalates and never falls to Off/none; with no lower level the selection is rejected. `unsupported` comes only from a positive report.
- Shipped-default regeneration: `fvm dart run tool/generate_model_capability_defaults.dart`; CI runs it with `--check`, and `test/tool/generate_model_capability_defaults_test.dart` asserts freshness. Every record is validated through `ThinkingControlOverride.parse`, the same schema users write.
- Family policy ids (`kimi_thinking`, `deepseek_thinking`, `zai_thinking`, `google_thinking`, `aggregator_upstream`, `nim_thinking`, `anthropic_thinking`) are route wire-dialect labels taken from the template. They select the request codec only, and `ThinkingRoutePolicy.policyIdFor` never consults the model id. The native `thinking.type` + `reasoning_effort` envelope is a declared wire (`native_toggle_effort`) admitted on first-party/partner native Chat dialects and the aggregator. Shipped-default route classes are data (`any`, `native`, `first_party`, `google`, `nim`); `first_party` withholds a record from the partner Chat route so that route's own models.dev evidence answers. Use it when live or catalog evidence for the partner contradicts the first-party record; never add provider scoping to the user `config.yaml` schema for this.
- Wire dialect is a transport property: a first-party native extension (`thinking.type`, a template kwarg, an aggregator envelope) is selected only from the admitted actual route dialect. Generic, local and custom Chat routes carry only the standard `reasoning_effort` field (and the generic `thinking.type` toggle for a reported toggle); custom routes consume no models.dev vendor entry and need settings or provider-reported evidence; a native extension additionally requires the normalized OpenAI-compatible Chat protocol, so an Anthropic or native-Ollama protocol never qualifies because of a configured API-mode string alone. An explicit validated model-only declaration may evidence a documented extension.
- Self-hosted-only facts (for example NIM Qwen template kwargs) are never advertised from hosted availability and require an explicit validated declaration.
- Exactly one finite typed `chat_template_kwargs` serializer serves the documented Boolean keys with a validated key allowlist; it is selectable only where the actual serializer can carry it (generic/custom Chat and the hosted NIM catalog), and aggregator, Responses, Messages and native-Ollama routes reject it before dispatch.
- One centralized finite vocabulary is shared by declaration validation and the typed serializers: a canonical effort-tier or level id must carry its own canonical value (no remap, elevation or downgrade, including a tier the wire does not support), while opaque ids may carry an explicit admitted value and numeric budget mappings remain a distinct legitimate budget contract. On Boolean kwargs and generic toggle wires a canonical effort-tier id rejects both Boolean values. A directive outside the admitted vocabulary, a negative Google budget, a non-positive Anthropic budget, or a directive the chosen serializer cannot carry fails actionably while the body is built; a Google zero budget remains the documented typed disable (`GoogleBudgetDirective(0)`). Omission is reserved for provider Default and never repairs an invalid value.
- Provider-default omission is a durable law: a null, empty or whitespace-only selection is `UseProviderDefault` for configuration and endpoint declarations alike, a known default remains descriptor metadata, and only an explicit valid selection dispatches a typed directive.
- A failed model-list refresh re-derives every cached descriptor from current authority (active Home configuration, config/credential revision, route protocol, actual API mode, persisted discovery metadata) and keeps it only when that reconstruction is `supported` from model-owned evidence (a models.dev entry or a model-only override) under the same capability revision; removed overrides, incompatible modes and config/credential revision changes fail closed, endpoint declarations stay route-owned and unresolved until a successful refresh, and live probe/discovery descriptors keep `live_probe_failed` invalidation.
- Provider setup is instance-first. Templates are immutable capability definitions; instances own editable metadata, credential revision, model choice, rate limit, and failover policy.
- Keep constants for protocol, auth method, credential action, requirement, and status centralized; do not branch on duplicate raw literals.
- Separate configured state from runtime readiness. Only a successfully verified current metadata/credential revision may become ready or default.
- Metadata or credential changes that invalidate verification must demote readiness.
- Provider-specific model discovery and generic model options must reuse one provider-owned implementation.
- Model discovery follows the instance protocol and retains selected/default plus curated fallback models when live discovery fails.
- Missing provider resolution returns a lazy error adapter rather than failing dependency composition or daemon startup.
- The dependency-composition default-adapter binding resolves the current runtime default on each lookup; it must never retain a missing-provider adapter across onboarding.
- Shared context services remain provider-neutral; each model turn supplies its live routed adapter explicitly.
- When a session/turn supplies no model, resolve the configured default dynamically; isolated tests without registered configuration may use the established safe placeholder fallback rather than crashing.
- Model capability declarations (`model_capabilities` in `config.yaml`) and intrinsic capability resolution are keyed solely by exact model identity; provider instance UUIDs, templates, and endpoints do not select or hint intrinsic metadata.
- Catalog lookups in `ModelsDevService` resolve intrinsic capabilities across catalog namespaces. Grounded aliases (`groundedModelAliases`) are strictly same-generation aliases only (no cross-generation fallbacks). Exact selected model ID is authoritative if present; when missing, contradictory candidate aliases within the same vendor fail closed (`null`).
- `ModelsDevService` catalog hydration is wired into daemon and standalone bootstrap lifecycles before turn admission is enabled, guaranteeing zero HTTP calls at admission/measurement/tool loops. Explicit provider model refresh (`manual: true`) forces catalog reload (`forceRefresh: true`), whereas background/startup uses TTL.

## Credential and State Storage
- Keep instance metadata/model cache/recent selections in the shared agent state database through the owning repositories.
- Open the agent state database through one shared connection; do not create a second handle for provider repositories.
- Keep provider secrets in the secret store keyed by instance UUID and expose only masked summaries outside the resolver. OAuth summaries may include display-only `account_label` and `account_name` derived locally from token claims; these values never become authorization state and raw tokens never cross the summary boundary.
- Credential mutation uses explicit keep, replace, or remove semantics; empty input never implies removal.
- When provider metadata and secrets share one Sanad Home boundary, mutating credentials must reconcile the secret store against authoritative instance UUIDs so replacement cannot preserve orphaned records; never prune across an explicit isolated state-home boundary.
- OAuth session storage remains separate from simple API-key configuration and Sanad auth.

## Message and Continuation Models
- `ViewImageMediaMetadata` owns byte-free image-result descriptors shared by internal completion callbacks and live/history projection; no source path, credential, or image payload belongs in a descriptor.
- `ToolExecutionResult` is the provider-neutral schema-v1 authority for ordered tool text/image blocks. Its `displayText` is derived from non-empty text blocks, image metadata and base64 shape are validated before construction, and unsupported schema/block/detail/error values fail closed.
- `Message.toolResult` is valid only for tool-role messages. When present, it is authoritative and compatibility `Message.content` must equal its derived `displayText`; legacy content-only tool messages remain valid.
- `Message.attachments` is an immutable ordered list valid only on user-role messages. `UserAttachment` and `UserAttachmentPolicy` are the sole schema/admission authority; durable JSON may contain the Agent-local reference, but event/history/cache consumers must use the path-free public projection.
- Separate visible `Message.thought`, `Message.reasoning`, final `Message.content`, and opaque typed provider continuation state.
- Provider state carries namespace and optional issuer, survives persistence, and may be cleared only explicitly for the matching owner.
- Preserve state-only assistant messages and typed terminal finish reason across restart.
- Turn-bounded semantic continuation remains distinct from network/runtime recovery retry.
