# Sanad Agent Contract

## Scope
This contract applies to `agent/`.

## Mission
- Implement only behavior explicitly requested or already established by source and current contracts; do not invent policy during maintenance.
- Keep the daemon runtime-authoritative for execution, provider state, tools, recovery, persistence, and client-facing runtime queries.
- Preserve clear dependency direction from entry-point composition to interfaces, engine, capabilities, evolution, core, and infrastructure owners.
- Keep local and cloud transports independent while sharing canonical protocol behavior.
- Keep architecture in `docs/` and operational procedures in agent skills; do not duplicate either in runtime contracts.

## Package Boundaries
- `agent/bin/` owns CLI, daemon, setup, service, and supervisor composition only.
- `agent/lib/cli/` owns the CLI transport, command-runner composition, and the command families. A command family keeps its family command as the single dispatcher in one file and gives each subcommand its own library under the family directory, so shared option, payload, and exit-code behavior has exactly one owner.
- `agent/lib/core/` owns configuration, identity/auth, provider runtime, shared models, and dependency composition contracts.
- `agent/lib/engine/` owns provider-neutral model execution, adapters, prompt assembly, tools loop, steering, and model-step state.
- `agent/lib/capabilities/` owns tool/skill/MCP catalogs, runtime context, permission policy, and tool execution contracts.
- `agent/lib/evolution/` owns sessions, memory, scheduling, titles, and durable runtime state.
- `agent/lib/interfaces/` owns platform adapters, gateway delivery, admission/orchestration, and canonical client protocols. A hosted `command == "dictation"` envelope is dispatched before conversation-session registration and must never create a session channel, session identity, or client tag.
- `agent/lib/infrastructure/` owns OS/platform and voice infrastructure implementations. `agent/lib/infrastructure/stt/` owns local dictation end to end: the catalog, the model store, readiness, the wire projection, and the session/transport contract. The whisper.cpp recognizer is `dart:ffi` inside this tree; the sherpa-onnx streaming recognizer is the swappable local package `agent/packages/stt_sherpa` (with `stt_sherpa_stub` for builds that cannot resolve `sherpa_onnx`), and the daemon only ever names its public surface. A catalog row carries the model's name, its locale description map, and closed-set codes — never sentences of the daemon's own — so adding a model is a catalog change only. A whisper.cpp row is decoded with the language it declares (`auto` only for a multilingual checkpoint, never for an English-only one, whose vocabulary has no language tokens), and `stt.language` describes a `stt.model_path` override rather than overriding a catalog row. Audio and transcript text never reach the logs, the model is loaded per session and freed on stop, and nothing there may spawn a sidecar, CLI, or local HTTP server. The whisper encoder window is a derived parameter, never the decoder's default: `audioCtxForSamples` (`stt_decode_params.dart`) sizes it from the buffered audio with a **measured floor of 448 mel frames**, because a bare proportional window decodes short utterances into phrase loops, and the full window costs 12.4 s of encoder time on the reference host for a 5 s press. Greedy decoding asks for **one** candidate per temperature tier, never whisper.cpp's five. The warm whisper context retains model weights only: every `sanad_whisper_run` creates and always frees a fresh `whisper_state`, because the pinned v1.9.5 flash-attention path can read stale padded K/V bytes when one reused state shrinks its `audio_ctx`; no decode state may cross a group or repetition-guard retry. Load allocates and frees one probe state so an unallocatable state fails at load, where the CPU fallback applies, rather than on every utterance. A group whose transcript repeats a 4-gram three times **and** outruns five words per second is re-decoded exactly once at the full window (`stt_repetition_guard.dart`), which is the only path that pays the whole-window cost; the throughput condition is required because a deliberate threefold repetition is speech, and re-decoding it at the full window loses content. Both parameters stay unit-tested and are applied in `sanad_whisper.c`, so no Dart-side change may leave the shim's `audio_ctx`/`best_of` wiring behind. Dictation session ownership is an opaque-owner lease released only after the session closes, and a session that never receives audio must not hold it: `start()` arms a first-audio watchdog that closes a session in which not one frame ever arrives, whereas silence *after* audio is legitimate and bounded only by the session limit. `status`/`install`/`cancelInstall`/`select`/`prepareRuntime` are served by one control surface for both channels (`docs/technical/dictation_transport_protocol.md`). A model install is **daemon-scoped**, never connection-scoped: only an explicit `cancelInstall` stops one, a repeated `install` of the same model joins the running one instead of starting a second writer, and `stt_status.install` is the in-flight truth every client rebuilds from, so a sheet reopen, a device switch, and a reconnect all see the same download. The download itself is bounded and resumable by law, because each property answers a measured defect: file bytes cross a bounded write pipeline — a writer isolate behind a fixed byte window (`kSttWriteWindowBytes`) with exactly one write in flight — so a fast producer can never queue the artifact in the heap and the socket read never idles for the disk, the page cache is forced out from a **separate flusher isolate** holding its own handle of the same file, every `kSttFlushWindowBytes` (64 MiB) of written bytes, because Linux defers writeback to `dirty_expire_centisecs` and the single fsync at close otherwise pays for the whole artifact (36.0 s transfer + 23.8 s tail on a 1.62 GB model, 27.1 MB/s end to end against a 54.7 MB/s disk) — and because an fsync is a blocking syscall on the caller's thread, doing it in the writer would only re-serialize the two phases (measured: 34.4 s end to end against 31.9 s), the writer is held to **two windows ahead of the last completed writeback** so the dirty page cache stays bounded and a slow disk paces the read, a request arriving during one flush is coalesced into one remembered request rather than a queue, `close()` waits for the running flush and then forces the tail on the writer's own handle so durability is unchanged, and a refused flush is the typed write failure (`storage_full` for `ENOSPC`), while a platform that refuses the flusher's own handle — or an isolate that cannot be spawned — **degrades to the close-only flush instead of failing the install**: one lifecycle line, no bound, no requests, so the overlap is lost and the artifact is not, so an install costs `max(network, disk)` and never their sum, a `.partial` is kept across every interruption and continued with `Range` before its size and SHA-256 are verified, the digest the verification compares is the OS implementation reached through `dart:ffi` (`stt_digest.dart`, CommonCrypto/libcrypto/bcrypt) with a pure-Dart fallback on a host that cannot load one — one native context per digest, closed by its owner on every path because native memory is not garbage collected, because a per-byte cost that runs on one core is what capped the download on a 4-core host, and a volume that cannot hold the artifact plus a safety margin is refused as `storage_full` before the first byte. Progress leaves the daemon through one coalescing emitter — at most one tick per 250 ms and one per 1 % of the total, plus the first, every phase change, and the terminal 100 % — so no transport can turn one install into a per-chunk storm, and the first tick of a resumed install carries the resumed offset rather than a zero the bar would have to contradict. It is announced (start), delivered (progress), and ended (terminal `stt_status`) to **every channel attached to the device**, so a sheet that was already open learns about a download another client pressed; the terminal status is published only after the install stops being truth, because a terminal payload built while it is still active states `install` again and leaves the client's row frozen until the sheet is reopened. The projection also states the bytes a resumed install already has on disk from its first moment — the payload is built before the first HTTP response, and a zero there restarts a resumed bar at 0 %. Those figures are cumulative across every artifact of the model, complete ones included, so a resumed multi-file model opens at its real share instead of at the pending file's share; only what the run still fetches is charged against the volume. A packaged Linux runtime is relocatable on its own — every shipped library records an `$ORIGIN` search path, and `--verify` proves it by asking the real loader from outside the folder — and it is built **portable, never native**: both builders configure `GGML_NATIVE=OFF`, Linux arm64 pins `armv8.2-a+dotprod+fp16`, and `--verify` disassembles the shipped libraries and fails on any instruction above the target's declared baseline (SVE/SVE2, I8MM, BF16 on arm64; AVX-512 on x64) because a hash, an architecture header, and `ldd` all pass on a `-march=native` build that traps with `SIGILL` on an older CPU. `docs/technical/native_stt_runtime_platforms.md` owns the per-target table. An engine that exists but cannot be loaded is a typed status (`engine_load_failed`, published with the lease released and a `dictation_error` beside it), never a daemon failure.
- The sherpa-onnx recognizer lives in the swappable local package `agent/packages/stt_sherpa` (package name `sanad_stt_sherpa`), never in `agent/lib`: `sherpa_onnx` requires the Flutter SDK, and the Linux arm64 Agent is built with the standalone Dart SDK. That lane selects `agent/packages/stt_sherpa_stub` through `agent/tool/pubspec_overrides.no_sherpa.yaml`, which exposes the same library name and public names with `sherpaEngineAvailable = false`. Both variants must keep that public surface identical, and neither may import daemon types. `agent/analysis_options.yaml` excludes `packages/**` from the package-wide analysis because only one variant can resolve; the lane that selected one analyzes it explicitly.
- Engine capability is one answer, not a platform test: `SttEngineAvailability` (`stt_types.dart`) decides which catalog entries are selectable, which rows the model sheet sees, and whether streaming/VAD exist. A build without sherpa is a complete batch-only build, never an error state; a session that names a sherpa model on it is refused with `model_unavailable`.

- `agent/tool/` owns release preparation and contract tooling. It is the single writer of tracked release-identity literals, including the `sanad-client` CLI version constant, so release identity is never advanced by hand.
- Generated-source tooling stays platform-neutral: manifest paths are validated in the POSIX context and joined with the platform separator, and every generated file or embedded asset is compared and hashed as canonical LF text, so Windows `core.autocrlf` checkout behavior can never report a clean tree as stale or embed different bytes per platform. `.gitattributes` pins `eol=lf` for those byte-sensitive paths.
- `agent/lib/interfaces/notifications/` owns every notification decision: which session event notifies, its kind and default urgency, the localized copy and its Client-key parity, the target, the escalation timer, and the withdrawal. One composer is the only writer of a notification payload, and every text field crosses the existing secret-redaction path and a bound there. The relay transports a finished, redacted instruction plus one target and reads no other field.
- `agent/lib/plugins/` owns generic lifecycle hooks only.

## Critical Cross-Domain Invariants

### Execution and Recovery Authority
- `SessionRunOrchestrator` is the sole admission and active-run authority. Durable work state decides running versus queued; in-memory busy, queue, suspension, and cancellation maps are projections only.
- Every turn is owned by session id, work-item id, immutable run id, and generation. Only the current owner may emit callbacks, commit terminal state, clear busy ownership, or drain queued work.
- Final delivery occurs only after a successful idempotent durable terminal commit for the exact owner.
- Stop invalidates the active owner before awaiting cancellation and atomically releases recovery, durable work, its durable interactive-wait checkpoints, and owned queued state without deleting newer-generation input. A stop also releases the in-memory partial-stream (`in_flight`) projection of the owner it stopped, so no runtime or query projection may keep reporting a stopped session as `running`; a blocked or waiting recovery releases that projection for its own run in the same way.
- Retry, resume, route change, and automatic failover require an atomic claim of the current durable owner; stale or concurrent losers are controlled no-ops.
- Recovery status is the daemon's verdict, never prose. A retryable failure with a scheduled attempt is `waiting` and carries its `retry_attempt`/`retry_budget`; only a non-retryable failure, an exhausted budget, or a cancelled resume is `blocked`. Every observer — the CLI, `session show`, and any delegated supervisor — classifies on the notice status plus the remaining budget, so a retry in progress is never reported as a stopped turn. The durable notice row is the same recovery state as the live broadcast, not a fallback: every non-`cleared` row projects into a session-history query with its counters, so a turn re-attached after a restart is never reported as having no recovery state.
- Crash recovery never replays a started tool without a durable result. Owned recognized checkpoints receive a neutral unknown-outcome result and continue automatically; only ownerless, malformed, or unrecognized state becomes blocked recovery.
- A resumable daemon shutdown must cross the global checkpoint drain and exit without session-wide Stop so startup recovery retains safe non-terminal work. Destructive shutdown requires an explicit cancellation mode and terminalizes owned work before exit.
- A managed daemon stop (`DaemonRestartCoordinator.stop()`) preserves unresolved interactive user-input waits (`system_ask_user` and tool-permission prompts awaiting decision) with their durable checkpoints intact and transitions active work to durable `waiting` without synthetic tool results or session cancellation, so startup recovery restores the pending decision. Explicit user stop continues to terminalize interactive waits.

### Engine and Context Authority
- `AgentRunner` is the single owner of conversation history, current-turn boundary, model loop, latest usage projection, and model-step lifecycle.
- Engine runtime collaborators mutate history through callbacks and cannot keep parallel history or current-turn state.
- `AgentContextAssembler` emits one system message ordered stable identity, workspace context, then volatile memory/date/runtime metadata.
- Provider adapters remain stateless and own wire translation only. Provider-specific endpoint/codec behavior must not leak into the runner.
- Context-pressure recovery after daemon restart may reuse persisted provider input usage only after the active adapter remeasures the exact historical request prefix; the next request must still prove a strict wire extension on the same route.
- Visible reasoning, final content, opaque provider continuation state, finish reason, and tool calls remain distinct typed data across streaming and persistence.
- Context continuity anchors are line-oriented and never match inside another word: a label at line start (optional markdown list/quote, heading or emphasis prefix) followed by a colon is an anchor, a mid-paragraph label is prose, and a label value too long to be quoted verbatim is report-only rather than critical. One anchor exists per label key.
- A summary repair instruction may name only `CompactionSummaryPrompt.allowedKeys`; continuity anchor labels are translated to their schema fields before any instruction is built, in the ordinary and the bounded recovery paths alike.
- A failed automatic compaction is durable and visible: the runner's automatic-compaction path is the only writer of that non-recovery `warning` runtime notice, and a warning never becomes recovery state, retry classification, or admission input.
- On echo-required Chat routes targeting thinking mode, same-route assistant tool turns replay the destination's interleaved reasoning field (empty string when the producer gave none) to satisfy provider protocol, while foreign and unrecorded turns remain unpadded.

### Protocol and Platform Authority
- `GatewayManager` routes typed delivery policy; it does not inspect event names to infer delivery or runtime meaning.
- `SanadProtocolBridge` dispatches/translates shared local/cloud canonical protocol. Focused handlers own workflows and receive dependencies explicitly rather than resolving hidden runtime owners.
- Delivery classification stays daemon-authoritative: a `steer` command marked `steer_only: true` may never become a turn, so `SessionRunOrchestrator` answers it with one typed `no_active_turn` rejection — correlated to the command's request id when it carries one, published uncorrelated otherwise — and never queues or admits the text; commands without the flag keep the admit-or-queue classification, and the flag is opt-in.
- Local and cloud Sanad transports remain independent adapters. Failure of one cannot stop the other or terminate the daemon event loop.
- Hosted attachment/media admission requires `supports_attachments=true`; each relay envelope independently requires `version: "v1"`. Binary bytes travel only in bounded relay chunks and never in canonical commands/events, logs, or durable public state.
- The hosted relay must stay bound to the live cloud socket. `io.io()` reuses one cached `Socket` per host whose `dispose()` clears every listener, so disposing the cloud socket (authorization loss, shutdown) must also forget the relay binding; otherwise the identity check in `initialize()` keeps the relay detached and relay events are dropped silently for the life of the process.
- The cloud path is outbound; the local daemon path is an inbound loopback server on a configured dynamic port.
- Runtime-rich turn input enters through typed interface models with explicit device, session, request, workspace, provider/model, thinking, origin, and delivery intent.
- A session's created projection carries the targeting its first turn was started with: an execution root without a registered workspace becomes `workspace_id = exec_root:<root>` with `workspace_path` and `metadata.execution_root`, and an owner turn's `allow_all_tools` becomes `metadata.permission_mode = full_access`, so a client can offer the session's own permissions before any `sessions_list` refresh. A turn that does not state its own tool authority inherits the durable session authority instead of resetting it to `false`, and the client changes that authority through `set_session_permission_mode`, which persists the session override and republishes the complete session payload.
- Workspace browsing, MCP, skills, slash commands, provider runtime, device settings, and session queries are daemon-owned services; clients render results but never become their source of truth.

### Persistence and Identity Authority
- Durable sessions, work items, notices, pending input, provider metadata, and route transitions use one shared agent-state database connection with one repository owner per table.
- The daemon and in-process standalone CLI acquire the same exclusive state-root ownership lease before opening the agent-state database; a second runtime fails closed and never competes for SQLite.
- The ownership lease is not anonymous: the winner records its pid plus the launcher id and runtime nonce it inherited in `.runtime-owner.json` beside the lock, written atomically through the Home boundary and carrying no credential. That record is diagnostic evidence for naming the holder in a refusal, never a second authority — the exclusive lock still decides, and a record whose pid is gone is reported as stale rather than trusted.
- Home selection has one owner and one order: an explicit `--home`, then an inherited `SANAD_HOME`, then the Home whose install record (`<home>/service.json`) sits beside a `<home>/bin/sanad` executable, then the OS user's default `$HOME/.sanad`. The record answers before the account default because an installed Agent belongs to the Home that installed it and a dedicated service account's `$HOME` *is* that Home: the default would name a second, empty Home, so `service status` would report a healthy unit as unowned and `service restart` would call it absent. Discovery is metadata-only and creates nothing: it stats the record (refusing a symlink) and reads no `.env`, credential, or other Home content.
- A Home-selected CLI call (`--home` or `SANAD_HOME`) resolves its local-gateway endpoint from that Home's own runtime record (`.local_gateway_endpoint.json`, written by the daemon after it binds and removed on every exit path that ends the runtime — a termination signal, a managed pause/stop through the coordinator's pre-exit cleanup, and the controlled restart whose successor republishes it) and fails closed when the Home has no live or owner-alive record; it never falls through to the default port or the worktree port scan. Inherited `SANAD_GATEWAY_URL`, `LOCAL_GATEWAY_URL`, and `LOCAL_GATEWAY_PORT` never override a selected Home, and an explicit `--gateway-url`/`--port` target must prove the same `home_id` as the selected Home. A record and a `/health` answer are evidence, not authentication: a missing `home_id` is tolerated only on the default Home's port `58085` (pre-`home_id` daemons), never for a named Home and never for a mismatching value.
- An endpoint that answered and refused the credential is running, not absent: with a selected Home, an authentication rejection (`401`/`403`) from an explicit or recorded target is `home_identity_mismatch` with exit `78` and no WebSocket connect, while a target that never answered stays "not running" so `--standalone` still works. Endpoint-resolution failures carry their discovery code as `error_code` in the `--json` envelope, and a daemon removes its runtime record only while that record still names its own pid, through one bounded hook that runs on every exit path — signal-driven exits and the managed stop alike — and a failed or stuck hook never blocks the exit. That signal-driven exit keeps a signal status — `128 + signal`, so `143` for `SIGTERM` and `130` for `SIGINT`, for the daemon and for the supervisor parent that owns it — never `0`, because a `0` after a signal is indistinguishable from a requested clean stop for `launchd` (`KeepAlive { SuccessfulExit = false }`), a shell, or `sanad-dev`.
- Platform supervisors agree with that signal status instead of reading it as a crash: the generated systemd unit declares `SuccessExitStatus=130 143`, so a requested stop ends `inactive` rather than `failed`, and a launchd stop unloads the job (`launchctl unload`, falling back to `launchctl bootout gui/<uid>/<label>`) because signalling a `KeepAlive { SuccessfulExit = false }` job relaunches it. A service definition that only carries a whole-body change is refreshed by `sanad service install`; the read-only `service definition` report compares the executable, arguments, Home, and instance only, and it reads the definition the queried Home's ownership metadata records — a system-scope unit included — instead of assuming the caller's own user unit.
- A Linux system-scope unit must be runnable by the account it names: the installer and `sanad service install` agree on one Sanad Home that account owns, `service install` proves that account can execute the unit's `ExecStart` and enter its `WorkingDirectory` before the definition is written, and the install health window re-reads the Home's local credential on every bounded poll instead of once. The ownership metadata inside that Home belongs to that account too, because the account is the reader that runs `service status` there; metadata that exists but cannot be read is reported as a permission problem with the remedy, never as an absent or unowned service. A definition that names another Home is that Home's service, so a Home that installed nothing answers `Missing` instead of reporting another Home's unit as its own unowned service. A failed install keeps its established credential handling and states that a retry needs fresh authorization.
- A root Linux install registers the dedicated unprivileged `sanad-agent` account and its Home whether root was entered directly or through `sudo`; `SUDO_USER` never selects the unit account, because the installer places the artifact from the effective uid alone and the two sides must not guess differently. `--run-as-user <account>` is the only explicit override: it must name an existing account, a non-root invocation may not use it, and `root` is accepted only when named, with a printed warning. A definition left for another Home is refused before download and pairing.
- Only a starting daemon rotates a Home's local-gateway credential, and only after its ownership lease and before it listens: `.local_token.home` binds `.local_token` to that Home identity, and a missing or foreign binding migrates on the next daemon start. Every other caller (`sanad login`/logout exchange, the CLI, `sanad-dev`) reads the credential read-only and can neither create nor invalidate it; a credential bound to another Home is treated as absent rather than presented.
- Read-only CLI inspection (`sanad schedule list`) is not a runtime: it takes no lease and opens the agent-state database only through `AgentStateDatabase.readOnlyAtPath`, never migrating or writing it. Schedule mutations stay with the daemon's `CronScheduler`.
- Admission, terminal commit, failover, stop cleanup, and cross-table execution transitions remain transactional through their aggregate owner.
- Every write transaction rolls back only while the connection still holds one, and always rethrows the original failure. SQLite already aborts a transaction for `SQLITE_FULL`, `SQLITE_IOERR`, `SQLITE_NOMEM`, `SQLITE_BUSY`, and `SQLITE_INTERRUPT`, so no boundary may turn that into `cannot rollback - no transaction is active`; `agent/lib/evolution/db/sqlite_transaction.dart` is the one owner of that rule.
- A full local disk is a typed local failure (`storage_full`), never a provider error: it is classified before provider failure text, carries its own title and message with no provider response body, and never fails over to another provider.
- `hardware_id` is persistent local machine identity and is distinct from backend-assigned device ids.
- `run_id` owns execution, `model_step_id` owns one model invocation, `tool_call_id` pairs tool use/result, raw `request_id` owns command correlation, and opaque `event_id` owns one canonical semantic event. `message_id` owns one persisted history record, `turn_id` owns one execution attempt's history records, and `history_revision` owns compare-and-swap for active-history mutations. Never substitute these identities for one another, for SQLite row ids, or for hydration indexes.
- A live root `user_message` is published only after its durable history row commits, and it carries the same message/turn/request identity and replay eligibility that subsequent history hydration exposes.
- Sanad auth, provider OAuth, provider secrets, durable state, and mutable worktree state remain separate storage concerns.

### Provider and Capability Authority
- The provider runtime is the sole authority for templates, instances, credentials status, model discovery, readiness, defaults, rate limits, and failover policy.
- `ProviderRegistry.profiles` declaration order is the setup presentation order for every surface: the CLI wizard, Client onboarding, and Client Settings render `ProviderCatalogService` output as-is. `opencode-go` is declared first on purpose; no surface may re-sort or re-group the catalog.
- Provider setup is instance-first. Only a successfully verified current revision may be ready or default; metadata/credential changes that invalidate verification demote readiness.
- Provider verification is daemon-owned: a live model discovery decides whether the configuration is wrong, and an opt-in generation probe against the instance's selected model adds route proof for the Test action. A `/models` listing alone never proves a credential to the user, so no surface may present a preset or fallback model list as verified.
- The generation probe never blocks setup: setup gates ask for discovery only, and only a definitive discovery failure (`invalid_credential`, `forbidden`, `endpoint_not_found`, other 4xx except `408`/`429`) may reject a credential. A probe that cannot prove the selected model — unselected model, non-chat catalog entry, rejected output bound, cold-loading local engine — is reported as a non-blocking warning and never changes the instance status. A probe `401` is the only probe result that may demote (`needs_auth`); a probe `403` is a warning, because discovery already accepted the key.
- Every provider failure leaves the daemon through one sanitized typed projection (category, HTTP status, short canonical reason, endpoint origin plus path, and `definitive`) and never as a raw response body, a header, or a credential. Only a definitive failure changes the status: `401` is `needs_auth`, a discovery `403` is `needs_auth`, other definitive HTTP failures are `error`, and a non-definitive cause (rate limit, outage, transport, timeout, unusable list, warning-grade copy) leaves the status untouched with the cause attached. Every demotion and every warning persists its cause on the cache row (`recordVerificationCause`), so the card explains itself after a restart. That classification is re-derived from the stored current-revision failure on every status reconcile, legacy raw rows are re-derived from their real text shapes (`HTTP <status>`, `LlmHttpException(<status> …)`, `SocketException …`) and rewritten to the sanitized form on read, and a verified re-discovery clears it.
- Legacy read-repair is one migration, not a second authority: a stored **definitive** cause that the current revisions still carry may never sit beside `ready`, so the reading path applies the same category → status mapping (`statusForDiscoveryFailure`) the mutation paths use and persists that demotion once — for a cause restored from raw legacy text and for a row an earlier build already sanitized into the structured form. The projection then carries that effective status, so the payload cannot contradict its own cause. Only a current-revision, definitive cause on a row still claiming `ready` is reconciled: the demoted status is the one-shot marker, so the repair cannot loop, a successful re-verification clears the cause and is never re-demoted, and non-definitive causes never move the status.
- Provider usage is a separate authority from instance status: a `provider.usage.result` of `auth_required` (missing or expired account token, or a usage endpoint `401`/`403`) never demotes an instance, never writes a discovery cause, and never blocks setup.
- Only the bare `sanad setup` wizard may be delegated to the injected interactive entry point; `setup list`, `setup status`, and `setup remove` execute their own `CliProviderSetup` implementation so `--json` cannot fall back to the wizard banner.
- `ToolsRegistry` and `LocalRuntimeCatalog` are the canonical execution/search and per-turn capability owners. `AgentRunner` executes their output but does not construct workspace, MCP, skill, web, or platform catalogs.
- `PermissionManager` alone enforces sensitive approvals and persists suspension before waiting. UI/platform responses cannot bypass policy or grant ownership.

## Global Runtime Laws
- Use `fvm` for every Dart operation.
- Keep `SANAD_HOME` stable for machine identity, auth, provider credentials, base configuration, and durable user-owned files.
- `sanad-dev` linked-worktree runs provide one isolated `SANAD_HOME` containing identity, credentials, sessions, memories, and request dumps; they must remove inherited `SANAD_STATE_HOME`.
- External and test harnesses may still use `SANAD_STATE_HOME` to redirect mutable state without relocating identity or provider credentials.
- E2E tests that initialize DI/SQLite or launch an agent process must set temporary `SANAD_HOME` and `SANAD_STATE_HOME` roots explicitly; Dart child processes must receive both variables instead of inheriting the caller's values.
- In-process suites that reach the runtime home boundary redirect it with `setSanadHomeOverride` and prepare that root before building the runtime, so a clean CI runner never depends on a developer machine's already prepared Sanad Home.
- Source worktrees consume global Sanad configuration and must not create a competing repository-local `.env`.
- Do not create hidden scratch or temporary directories inside the repository.
- Missing provider configuration must not prevent daemon startup; fail lazily when an LLM operation actually requires a provider.
- No Agent start performs an unbounded operating-system credential-vault call, and no daemon starts an OS authorization dialog. A daemon opens its vault without waiting (`SecretVaults.beginOpen()`), reports `opening|available|unavailable`, and degrades a credential it has not read yet as `vault_not_ready` rather than absent; a prompt comes only from the explicit `sanad vault authorize` grant.
- Local/offline provider configurations remain valid and must not require an OpenAI-style key.
- Sensitive payloads,tokens,provider secrets,pending steer text,recovered draft text,command payloads,event/final-answer content,custom Client names,and raw Client-instance identity must not enter logs;transport diagnostics are lifecycle/type/count metadata only.
- Platform failures and asynchronous command failures must be contained so one transport cannot terminate the daemon or other interfaces.
- The in-process hot-restart supervisor is bound to the launcher that started it. A managed launch injects `SANAD_DEV_LAUNCHER_ID`/`SANAD_DEV_RUNTIME_NONCE`; before every respawn the supervisor must find a launcher lease for the owning Home that still names that id and nonce, with a live `launcher_pid`, and must otherwise exit without spawning. Its stdin end-of-file is that launcher's death and ends the supervisor the same way, while a manual launch without the identity keeps the unmanaged behaviour. Consecutive child failures — not failures inside a wall-clock window — end it after five, with a capped 0.5/1/2/5/10 s backoff and one bounded reason, so a ~5 s failure cadence cannot restart forever. Each lifecycle transition is one line in `<home>/logs/agent-supervisor.log`, bounded and rotated, because the launcher-owned journal dies with the launcher.

## Development and Testing Requirements
- Analyze every code change with the FVM-managed Dart analyzer before completion.
- Resolve `agent` dependencies with `fvm flutter pub get`, not `fvm dart pub get`: the local speech engine (`sherpa_onnx`) ships as a Flutter plugin package and is consumed through its FFI API only. The binary is still built with `fvm dart compile exe`, and no `package:flutter` import is allowed outside that dependency boundary.
- Run focused unit tests for the changed owner and every directly affected contract boundary.
- Run the full fast suite for broad engine, interface, provider-runtime, persistence, capability-registry, or shared-model changes.
- Require daemon-backed E2E only when mocks cannot validate the boundary: local/cloud socket contracts, daemon bootstrap/lifecycle, persistent runtime state and restart recovery, provider readiness/model execution, worktree runtime isolation, or end-to-end session execution.
- When interface/runtime ownership changes affect the local daemon contract, add or update real daemon-backed coverage rather than relying only on mocks.
- Unit tests for retry, polling, scheduling, or asynchronous delivery inject deterministic wait/control seams or await the exact emitted event; they must not sleep through production backoff, polling intervals, or padded settling windows.
- A wait that crosses a thread, process, port, or file-lock boundary observes the state it needs — a completer, a readiness line, a lock outcome — instead of counting event-loop turns, and its fixed budget is a failure deadline of at least 3× the measured worst case on the slowest release lane, never a short timer used as synchronization. A platform-dependent default is asserted through its owning resolver in the test that consumes it, so no assertion restates a host-specific literal.
- A real-CLI test spawns the compiled kernel artifact owned by `test/support/compiled_agent_cli.dart`, never `dart run` once per case: compilation is the expensive part of the test, so it happens once per suite, `kernel()` stays lazy so the first case owns the generous timeout, and a suite that proves a different composition entry point names it (`entrypoint: 'bin/daemon.dart'`) instead of falling back to `dart run`.
- A test never assumes the host or the network: the whole suite runs on Linux x64 and arm64 in the release lanes (with and without the sherpa engine) and on macOS arm64 and x64 in the post-merge `macOS full suite` workflow. Host-specific expectations come from the owning resolver (`Abi`-aware helpers such as `defaultSttUseGpuFor`, `SttEngineAvailability`/`usableSttEntries`/`defaultUsableSttEntry`, `SttNativeTarget`), an arch-dependent fixture takes the target as an explicit input, and no unit test downloads from a live third-party URL.
- A local loopback harness never treats a released probe port as owned: it binds each attempt on a freshly reserved ephemeral port and re-reserves on an address-in-use collision, so a concurrent suite can never fail it and no fixed port is acceptable.
- Tests may never open the real Sanad Home. Home-owning stores (agent-state database, secret vault, default secret store) fail closed under the Dart test runner without explicit isolation and for the OS user's real default Home; fix a failing test by isolating it, never by weakening that guard. Tests and E2E subprocesses never reach the OS credential vault through the default secret store, and the E2E runtime refuses to start on the real default Home or without a state root separate from its identity Home.
- Every spawned test daemon uses a unique temporary `SANAD_STATE_HOME`, cleans it after shutdown, and preserves the normal shared identity/configuration boundary.
- Daemon-backed tests use the deterministic E2E provider and must never inherit the live agent database, invoke the user's configured provider, or mutate user runtime state.
- A committed fixture or test-data file never ends in a suffix the private Production deploy artifact check rejects — `pem`, `key`, `p12`, `pfx`, `dump`, `sql` — because that host rejects such archive members, in this package and anywhere else in the public repository. Keep the real format as a trailing double extension (for example `test/evolution/fixtures/agent_state/legacy_pre_112_schedules.sql.txt`) and update every reference; `test/guards/deploy_artifact_suffix_guard_test.dart` enforces the rule over the Git index, and only `client/release/shared/dsa_pub.pem` is allowlisted because both clients embed it.
- Documentation-only contract changes require documentation generation/lint integrity but do not require Dart analysis or runtime tests unless source code also changes.
- Every Agent CLI option is part of the cross-package relay grammar contract (`agent/test/fixtures/cli_relay_grammar.json`, generated by `agent/tool/generate_cli_relay_grammar.dart`): adding, renaming, aliasing, or removing an option or abbreviation requires regenerating that contract in the same change, because `sanad-client` resolves a relay approval target with the same grammar.

## Definition of Done
- Ownership and dependency boundaries remain intact with no duplicate state authority.
- Relevant focused tests cover behavior and failure/recovery paths.
- Analyzer and required test scope pass.
- Full-suite and E2E results are reported only when required by the blast-radius rules above.
- A new or grown non-generated `lib/` file stays inside the size ratchet: over 1000 lines it fails `test/guards/file_size_ratchet_guard_test.dart`, and an allowlisted file never exceeds its recorded count; split the file instead of raising the number.
- Runtime-law changes update the nearest contract and active design documentation in the same session.
