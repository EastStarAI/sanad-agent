## Correction record — bounded independent-review repairs

Both review findings were repaired in the same worktree and session; no runtime, Home, browser or Client action ran, and no nested delegation, commit, push or PR was performed. Failing and passing command logs live outside the repository (`.logs/` under the worker root, referenced by the external report).

Unfinished regression first repaired: the predecessor's failing same-route regressions were present but the harvested `_TestSessionCubit` insert collided with the existing one, leaving an orphan `@override` block and a duplicate class. `fvm flutter analyze` reported 5 issues (`invalid_annotation_target`, `super_in_invalid_context`, `expected_executable`, `unused_element`, `duplicate_definition`) before the merge; after merging the two harness declarations into the single `thinkingWrites`-tracking class the analyzer is clean. The two regressions then failed for the real reason (RED: 2 failing / 2 passing in the 77K group).

- Same-route conversation admission (`_checkRouteChanged` previously compared provider/model/device only): the selector now tracks the resolved conversation (`_lastSessionId`) separately from route identity, so a conversation change on an unchanged route re-resolves the effective selection for the *newly* selected conversation from the already resolved descriptor. The admission is owner-gated: it is dispatched only when `ConversationInputState.activeSessionId` is the conversation being resolved, and a composer that still owns another conversation is retried from its own ownership change (`BlocListener<ConversationInputCubit, ConversationInputState>`). A resolution that finishes after a switch always reads the *currently* selected conversation, so a stale/in-flight snapshot cannot write onto the conversation it started for, and a valid explicit choice in either conversation is never rewritten.
  An owner-retry reads the composer's published state for the value the route already carries rather than this widget's `inputSlice`: that slice is a projection built for the previous frame and still held the conversation just left, which made a fresh conversation look already admitted and suppressed its own default.
- Actual admission evidence: `client/test/widget/route_thinking_mode_real_preference_test.dart` mounts the control over the real `ConversationInputCubit` (real `selectThinkingMode`) and the real `SessionMessagesCubit` with fake conversation/preferences repositories, rebuiling the input slice from composer state as the production composer does, and asserts the admitted option in real next-send state (`nextMessageThinkingMode`, the value the send path reads), in the persisted device preference, and in the conversation-scoped `updateSessionPreferences` write. Covered: an unset conversation, a same-route sibling conversation (each receiving its own default, neither written twice), and an explicit `Off` that is never rewritten to the default and comes back with its own conversation.
  The harness lives in the same file the widget contract documents; a bounded `settle` helper keeps a non-settling tree failing fast instead of hanging.
- Menu-only provider-default hint (confirmed continuation): the declared native default is disclosed by one `thinkingModeProviderDefaultHint` line rendered inside the expanded menu below that option's own row, beside any budget annotation the row declares. The chip, tooltip and every other row are unchanged, so no persistent surface claims a provider default; a route whose declared default is unknown or absent marks no row (`_ThinkingMenuEntry.isNativeDefault` is set only from `RouteThinkingControl.nativeDefaultOption`).
- Strongest-first display reversal (confirmed continuation): `_menuEntries` renders the declared options (and the legacy device list) reversed for display only, keeping exact ids, the finite set, dispatch values and native metadata. Tests that encoded the previous order were updated to the reversed order, and the two rows that legitimately carry the hint now assert it explicitly instead of `isNull`.
