# 77I D3 — OpenCode Go vision investigation

## Outcome

The reported omission is generated by Sanad before provider submission. It does not establish that OpenCode Go or `deepseek-v4-flash-vision-exp` rejected an image. This initial investigation was read-only; subsequent authorized implementation and successful live Go acceptance are recorded in [77I2](77i2-openai-compatible-tool-image-projection.md).

## Verified source evidence

- `agent/lib/engine/adapters/provider_registry.dart`: OpenCode Go uses `chat_completions`.
- `agent/lib/engine/adapters/base_openai_adapter.dart`: tool messages unconditionally use `textOnlyToolResultContent`.
- `agent/lib/engine/adapters/llm_adapter.dart`: adapters without an explicit media capability default to text-only; the omission marker is locally generated.
- Reference corpus `refrence_projects/opencode/packages/opencode/src/session/message-v2.ts`, around lines 150–173, 310–325 and 394–414: OpenAI-compatible routes extract media from tool results, retain textual results, and inject media in a synthetic user message. Native tool-media support and model image-input support are distinct capabilities.
- Reference corpus `refrence_projects/hermes-agent/agent/vision_message_prep.py`, around lines 216–233: Hermes also distinguishes model vision from provider acceptance of list-type tool content. Its text-summary fallback is not proof that the model lacks vision and is not the preferred fix for this case.

## External evidence reviewed 2026-10-13

- [OpenCode Go documentation](https://opencode.ai/v2/docs/console/go): lists DeepSeek V4 Flash Vision Exp as available through Go.
- [OpenCode model usage page](https://opencode.ai/data/deepseek/deepseek-v4-flash-vision-exp): explicitly lists Text and Image inputs.
- [OpenCode Go model catalog](https://models.opencode.ai/providers/opencode-go): lists exact ID `deepseek-v4-flash-vision-exp` with an OpenAI-compatible provider package. Current catalog advertises a different base URL from Sanad's tracked default; legacy compatibility and the configured runtime endpoint must be checked before considering any endpoint migration. This is not an established cause of the omission.
- [DeepSeek vision documentation](https://api-docs.deepseek.com/guides/vision/): documents image input using Chat Completions content blocks. It says its legacy vision-exp alias now resolves to the latest Flash model on DeepSeek's own service; do not assume that Go uses the same alias migration.

## Scoped repair design

1. Resolve image-input capability from explicit provider/model metadata; do not infer it from a name containing `vision` and do not enable all Chat Completions models.
2. Keep the authoritative canonical rich tool history unchanged. At the adapter wire boundary, retain textual tool results with their original call IDs and project verified image bytes using user-role `image_url` data URL blocks.
3. Insert synthetic image context only after the complete contiguous tool-result batch, preserving parallel tool-call/result pairing and indicating tool provenance without exposing local paths. This is model input derived from tools, not a persisted user turn or a new user instruction.
4. Use the same projection for sync, streaming, outbound measurement and continuation/replay. Preserve pruning, media bounds and unknown/text-only fallback.
5. Correct the omission explanation so an unsupported Sanad projection is not presented as an observed provider rejection.
