# المهمة 87 — تكافؤ هوية وترتيب المحادثة بين البث والتاريخ والعملاء

## الحالة

- **الحالة:** اكتمل التنفيذ والتحقق الآلي للنطاق الموسّع. دُمج `main` الأحدث بعد تعذر أول جولة مرئية بخطأ المزود، ونجحت analyzers والحزمتان الكاملتان بعد حل التعارضات. الخطوة التالية إعادة تشغيل runtime الاختباري ثم استئناف التحقق المرئي.
- **الفرع الحالي:** `feature/87-live-turn-identity-and-steer-ordering` داخل `.agent/worktrees/87-live-turn-identity-and-steer-ordering`.
- **البوابة الحالية:** G4 — إعادة تشغيل الوكيل والعميل من المصدر المدمج ثم إعادة التحقق المرئي الحي.
- **نسبة العمل المتبقي:** نحو **4%**، محصورة في التحقق المرئي الحي المصرّح به ومراجعة المالك؛ التنفيذ واختبارات الوحدة والتكامل وdaemon-backed E2E مكتملة.
- **حدود التسليم الحالية:** تنفيذ وتحقق داخل Worktree المهمة؛ لا Commit أو Push أو PR أو Merge، ولا `sanad-dev switch` أو `sanad-dev stop` أو تشغيل runtime حي دون إذن منفصل.

## الهدف

جعل الإسقاط الحي للمحادثة مطابقًا للإسقاط السلطوي بعد إعادة تحميل التاريخ، بحيث
تحمل أحداث الدور الحية هوية سببية ثابتة، ويظهر الـpending/delivered steer في
الموضع الذي استلمه فيه الوكيل فعليًا، وتزيل عملية Edit/Retry المقبولة الدور
القديم فورًا دون أن تعيد الأحداث المتأخرة أدواته أو رسائله. يشمل ذلك الرسائل
العادية المرسلة أثناء idle، ودمج الذاكرة مع الصفحات، وتكافؤ الأحداث الدائمة
لدى عملاء مستقلين متصلين بالوكيل نفسه، دون جعل Client سلطة على ترتيب التاريخ.

## المشكلة المثبتة

هناك خمس فجوات تشترك في أن العرض الحي لا يصالح العمليات مع الحالة السلطوية
وهويتها بصورة مكتملة: العرض يعتمد جزئيًا على ترتيب وصول الأحداث
وهويات جزئية، بينما التاريخ يعتمد على الرسائل المحفوظة وترتيبها السببي.

1. يرسل Agent أحداث `tool_use` و`tool_result` و`thought/reasoning` الحية بهويات
   التشغيل مثل `run_id` و`model_step_id` و`tool_call_id`، لكنه لا يضمن حملها
   `turn_id`. بعد قبول Edit/Retry يحذف Client العناصر المطابقة لهوية الدور فقط،
   فتظل الأحداث التي لا تحمل الهوية وتظهر رسالة المستخدم البديلة بعدها.
2. يضع Client الـpending steer داخل قائمة أحداث المحادثة فور وصوله. إذا ظهرت
   أداة لاحقة قبل أن يستهلك الوكيل الرسالة، تبقى الرسالة في موضع وصولها الأول.
   عند التسليم لا يحمل حدث lifecycle مرجعًا سلطويًا لموضع الإدخال، لذلك لا يعيد
   Client تموضعها. إعادة تحميل التاريخ وحدها تضعها بعد الأداة الصحيحة.
3. يقبل مسار `Queue -> Steer` نص الرسالة في Client، لكن الانحدار الذي دخل في
   commit `987a7c8f4b31bf1780d1daadde0f68bb2eb518c1` أسقط حقل `message` من أمر
   `steer`. يصل النص فارغًا إلى Agent، فلا ينفذ التحويل الذري من queued إلى
   pending steer. تبقى الرسالة في الطابور، وتظل عملية الواجهة في loading إلى أن
   يعيد تبديل المحادثة إنشاء الحالة المحلية، من دون أن يصلح الحالة السلطوية.

4. **تكرار الرسالة العادية عند إعادة الفتح:** أثبت التحقيق على `main` أن
   `_mergeRetainedHistoryWithHydration` يطابق `event.id` فقط، فيحتفظ بالرسالة
   الحية ثم يلحق نسختها التاريخية ذات event identity المختلفة رغم تطابق
   `message_id` و`request_id`. أعاد اختبار تشخيصي مؤقت باستخدام mapper/store/
   commands الحقيقيين واستجابة سجل محاكاة ترتيب `user -> tool -> user -> final`؛
   أعطى السجل نفسه بمخزن نظيف `user -> tool -> final`. لم يكن ذلك فحصًا مرئيًا
   لمحادثة المستخدم، ويجب تحويل الدليل إلى اختبار انحدار محفوظ.
5. **إعادة إنشاء delivered steer خارج الصفحة:** يحتفظ Client بسجل lifecycle
   مسلّم، ثم ينشئ فقاعة بديلة عند غياب الرسالة الأصلية عن tail المحمّل؛ تحميل
   صفحتها الأقدم يصالح الهوية ويزيل الفقاعة. إضافة anchor وحدها لا تكفي إذا
   كان المرجع أو الرسالة خارج الجزء المحمّل. الاختبار التشخيصي السابق أثبت
   المسار في مخزن العميل؛ يجب تثبيته ضمن اختبارات المهمة.

## القرارات المثبتة

### 1. ملكية الهوية والترتيب

- Agent هو المالك السلطوي لـ`turn_id`، وحدود model steps، وموضع تسليم الـsteer،
  و`history_revision`.
- `event_id` يعرّف حدث النقل ويمنع تكراره، و`tool_call_id` يربط بداية الأداة
  بنتيجتها، و`message_id` يعرّف سجلًا دائمًا، و`turn_id` يربط كل أحداث محاولة
  التنفيذ الواحدة. لا يحل أي معرّف منها محل الآخر.
- لا يستخدم Client timestamp أو ترتيب وصول Socket كسلطة نهائية لترتيب حدث
  دائم. ترتيب الوصول يجوز فقط لإظهار حالة مؤقتة إلى أن تصل الهوية السببية.
- يجب أن تحمل كل أحداث الدور الحية التي يمكن أن تبقى في الـtimeline
  `session_id` و`run_id` و`turn_id`، مع `model_step_id` و`tool_call_id` حيث
  ينطبقان. لا يُختلق `message_id` لحدث غير محفوظ.

### 2. دورة حياة الـpending steer

- يظهر الـpending steer فور قبول Agent له، لكنه يظل projection مؤقتًا لا يثبت
  موضعًا دائمًا داخل transcript.
- أثناء `pending` أو `delivering` يبقى المؤشر بعد أحدث نشاط تنفيذ معروف في الدور؛
  لا يجوز أن تظهر أداة جديدة تحته وكأن الوكيل استلم الرسالة قبل تنفيذها.
- بعد الحفظ والتسليم يرسل Agent حدثًا سلطويًا يحتوي هوية الـsteer الدائمة،
  `turn_id`، `history_revision`، ومرجع موضع سببي ثابت إلى الأداة/الرسالة التي
  تم التسليم بعدها؛ ويجب حفظ هذا المرجع وهوية التسليم ذريًا داخل نفس
  معاملة (transaction) قاعدة البيانات التي تثبت التاريخ قبل نشر الحدث.
- يستبدل Client الـprojection المؤقت بالحدث الدائم مرة واحدة وينقله إلى موضعه
  السببي. إعادة الفتح، pagination، cache hydration، والتنقل السريع `A -> B -> A`
  والبث الحي يجب أن تنتج الترتيب نفسه دون duplicate أو تسرب بين الجلسات.
- Cancel يظل متاحًا للـpending فقط وفق lifecycle الحالي، ولا يتحول الإخفاء
  المؤقت إلى حذف متفائل من التاريخ.

### 3. مصالحة Edit/Retry

- لا يغير Client العرض الدائم قبل نتيجة `session.turn_replay_result=accepted`.
- تحمل النتيجة المقبولة هوية الدور المستبدل، هوية الرسالة البديلة، وrevision
  السلطوي الكافي للمصالحة.
- بعد القبول يخفي Client الرسالة الجذرية المستهدفة وكل projection تابع لذيلها،
  ويحفظ tombstone لهوية الدور/التشغيل القديم حتى لا تعيده نتيجة أداة أو stream
  متأخرة.
- يجب أن يبقى fallback سلطوي لإعادة تحميل tail عند غياب الحد المحلي أو تعارض
  revision؛ لا يُخمن Client الحد من النص أو timestamp.
- تحافظ المصالحة على كل الأحداث السابقة للرسالة المستهدفة وعلى صفحات التاريخ
  الأقدم وموضع القراءة.

### 4. التوافق والترحيل

- تدعم الواجهة الأحداث القديمة ناقصة `turn_id` أثناء فترة التوافق: لا تُترك
  مرئية بعد replay مقبول، ولا تُربط بدور جديد اعتمادًا على التخمين.
- لا يتطلب الإصلاح rewrite لقاعدة بيانات المستخدم. السجلات الدائمة الحالية
  وهويات الـsteer التي يستعيدها history تظل المصدر السلطوي.
- أي إضافة لحقول protocol تكون backward-compatible مع العملاء الأقدم، وتفشل
  بصورة آمنة عند غياب مرجع الموضع.

### 5. تحويل Queue إلى Steer

- يرسل Client النص الأصلي مع الهوية المستقرة عند طلب تحويل queued message إلى
  steer؛ لا يجوز إعادة بناء النص من الـtimeline أو cache ثانوي.
- يظل Agent مالك التحويل الذري: إلغاء queued work وإنشاء pending steer بالـraw
  request ID نفسه، أو إرجاع نتيجة نهائية صريحة تشرح لماذا لم يحدث التحويل.
- تحمل نتيجة العملية ارتباطًا بهوية الأمر والرسالة المستهدفة وoutcome typed مثل
  `promoted` أو نتيجة رفض/فشل، كي يصالح Client صف Queue وPending projection
  وحالة loading مرة واحدة.
- عند `promoted` يختفي صف Queue ويظهر Pending Steer بالنص والهوية نفسيهما دون
  duplicate. وعند أي نتيجة نهائية أخرى تنتهي حالة loading وتعود الأدوات وفق
  الحالة السلطوية بدل الاعتماد على مغادرة المحادثة والعودة.
- لا تشمل هذه المهمة إعادة نص queued أو pending steer إلى composer عند Delete أو
  Cancel؛ الاستعادة المعتمدة تظل خاصة بمسار Stop الحالي.

### 6. مصالحة المحادثة العامة وتعدد العملاء

- Agent يملك الهوية الدائمة والموضع السببي ونسخ الحالة، ويصدر بيانات متسقة
  عبر live/history وLocal/Cloud لكل العملاء. تثبت هوية الرسالة الدائمة قبل
  نشر قبولها؛ لا يُختلق message id لجزء stream غير محفوظ.
- يحدد التصميم في G3a عقد موضع سببي ثابت للأحداث الدائمة مستفيدًا من بنية
  التاريخ والـanchors الموجودة. `history_revision` نسخة للتاريخ وليس مفتاح
  ترتيب لكل أحداثه، وrevision lifecycle ليس موضع الرسالة. لا يلزم Event
  Sourcing شامل أو تسلسل عالمي عابر للجلسات لحل هذه المشكلة.
- Client يملك reducer واحدًا لمصالحة الهوية والموضع في الذاكرة والصفحات
  والأحداث الحية؛ يطبق حقائق Agent ولا يستنتج النتيجة من ترتيب الشبكة أو
  timestamp أو النص. Widgets لا تملك dedupe أو فرزًا بديلًا.
- تميّز المصالحة event/message/turn/tool/model-step identities حسب نوع الحدث
  ونطاق الجهاز والجلسة. `message_id` هو مرجع الرسالة الدائمة؛ أي fallback
  بـ`request_id` يكون محدودًا بنوع الحدث وعقده، فلا يدمج كل أحداث الدور أو
  محاولات replay، ولا يدمج رسالتين مختلفتين لهما النص نفسه.
- السجل يحدد ترتيب الجزء الذي يغطيه. غياب رسالة عن صفحة ليس حذفًا ولا إذنًا
  بإلحاقها بالذيل. تبقى الصفحات الأقدم والأحداث الحية الأحدث محفوظة دون خلط
  نسخ متعارضة؛ عند فقد الموضع أو تعارض النسخة تُطلب مصالحة سلطوية محدودة
  ومجمعة بدل التخمين أو إعادة تحميل غير محدودة.
- حالة pending/delivering مؤقتة منفصلة عن transcript الدائم. لا تعيد حالة
  delivered القديمة إنشاء فقاعة خارج الصفحة؛ ويُحفظ العرض الحي المقبول حتى
  المصالحة دون حذف مبكر. معلومات منع replay المتأخر لا تمنح حق إنشاء صف جديد.
- المقارنة بين العملاء تخص هوية وترتيب الأحداث الدائمة عند تساوي نطاق السجل
  ونسخته؛ لا تشترط تزامن الشبكة أو تطابق reasoning المؤقت أو viewport.
- الأحداث القديمة ناقصة الهوية/الموضع تستخدم توافقًا محدودًا ومصالحة من
  Agent، لا استنتاجًا من النص أو الوقت؛ لا إعادة كتابة جماعية لتاريخ المستخدم.

### 7. الاعتماد وترتيب التنفيذ مع المهمة 78

- تملك هذه المهمة إصلاح تكرار الرسائل العادية، وإسقاط delivered steer خارج
  الصفحة، والعقد المشترك لهوية وترتيب live/history/العملاء؛ لا تنشأ مهمة
  موازية لهذه الإصلاحات.
- تُستكمل 87 بالنطاق الموسّع، وتغلق G3a وG4 ومعايير القبول والتحقق المرئي
  المصرّح به، ثم يُعتمد أساسها المتحقق منه قبل بدء تنفيذ 78. نقل التغييرات
  أو Commit/Push/Merge أو تغيير runtime يظل محتاجًا إذنه المنفصل.
- تستهلك 78 العقد نفسه لإشارات Route Transition وCancel/Stop؛ لا تعيد تصميم
  ترتيب مستقل أو تطور مخازن المحادثة بالتوازي مع استكمال 87.

## داخل النطاق

- مصالحة الرسائل العادية والـsteer عبر البث والتاريخ والذاكرة والصفحات والعملاء؛
- تمرير `turn_id` عبر ActiveRun/GatewayResponse والأحداث الحية التابعة للدور؛
- إضافة عقد سلطوي لموضع وهوية الـdelivered steer؛

- مصالحة Edit/Retry المقبولة مع الذيل المرئي ومنع late-event resurrection؛
- تكافؤ Local Gateway وCloud envelope لنفس حقول الهوية؛
- اختبارات Agent وClient وdaemon-backed E2E والعرض الحي مقابل history؛
- تحديث وثائق المنتج والبروتوكول وQA والعقود القريبة إذا تغير قانون دائم.

## خارج النطاق

- إظهار أو تنفيذ Edit/Retry على pending أو delivered أو embedded steers؛
- إنشاء replay boundary داخل الدور أو إعادة تنفيذ الوكيل من منتصف tool chain؛
- تغيير سياسة tool side-effect confirmation أو compaction؛
- تغيير queue semantics الأخرى أو provider continuation semantics؛
- إعادة نص queued أو pending steer إلى composer عند Delete أو Cancel؛
- تغييرات Markdown أو Terminal presentation أو viewport scrolling غير اللازمة
  لإثبات ترتيب الأحداث؛
- migrations تعيد كتابة سجل المستخدم القديم؛
- Commit أو Push أو PR أو Merge قبل إذن جديد صريح من المالك.
