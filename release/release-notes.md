# Sanad 1.0.22

Sanad 1.0.22 adds dictation: the composer microphone sends speech to the Agent, the Agent transcribes it on a local in-process engine or through the hosted relay, and the transcript streams back into the composer. The release also publishes the Agent for Linux arm64, makes a dictation runtime failure disable dictation instead of the install, and closes a set of long-running-precondition defects — the daemon grows no longer, a durable runtime notice is readable by every reader, a run session keeps the permissions it was created with, and no startup path waits on the OS secret vault.

## Dictation

- **The composer can dictate.** A microphone action sits in the composer's action row, beside the model and thinking-level selectors, and only appears when the connected device advertises dictation. While a session is active the button is a Stop control and the live meter takes the row's width, with the permission picker, model selector, and thinking-level selector stepping aside and returning unchanged. Insert, retry, and cancel behave as they do elsewhere: the transcript is inserted once at the caret and is never sent on the user's behalf (#337).
- **Two channels share one pipeline.** A local `/ws?type=dictation` channel runs an in-process engine; the hosted `dictation_relay_v1` capability carries the same work through the relay with request, route, and sequence identity, binary PCM framing, origin-only delivery, admission limits, and TTL cleanup. Both channels use one `DictationService`, so lease, engine, residency, and vocabulary behave identically, and neither creates a conversation session, session identity, or client tag — the existing voice path and its origin correlation are untouched (#337).
- **Readiness includes the model.** A device that reported `Ready` with no model installed started a session the daemon refused with `model_not_installed`, showed no install sheet, and Settings showed `Ready` for the same state. `readiness()` now resolves the model a session would actually load and reports `model_not_installed` or `sherpa_runtime_missing`, so `stt_status`, the settings projection, and the session start agree; every reason has an en/ar sentence and one route to one sheet, and the device settings card opens that same sheet as its install action (#337).
- **A model row is identity, not copy.** Catalog rows carry `name` (a proper noun), `description` (an `{en, ar}` locale map), `badge` (a closed set), `speed_tier`, `size_bytes`, `streaming`, and `location`. Rows render the name, badge, description, size, speed bars, and a streaming icon with installed models first, and adding a model is a catalog change with no Client change (#337).
- **A dictation session is bounded.** Voice activity detection opens and closes a bounded session of batch finals, so a hold-to-talk gesture produces exactly one final for one clip, and the transcript never arrives in pieces the composer has to reassemble (#337).

## Dictation runtime and packaging

- **A runtime failure disables dictation only.** Downloading and verifying the `agent-runtime` archive used to be part of the install and update contract, so a checksum mismatch, an unreachable mirror, or a rejected layout could fail the whole Agent install for a feature that only ever carries dictation. A failure is now recorded in one marker (`.runtime-install-failed`) with a closed cause vocabulary — `runtime_download_failed`, `checksum_failed`, `trust_failed`, `layout_rejected`, `replace_failed`, `install_failed` — and reported as one stable readiness reason, `native_runtime_install_failed`. The bundle, the updater, the bootstrap installer, and both `install.sh` and `install.ps1` warn, restore the predecessor runtime when they can, record the cause, and exit successfully; the settings card and the model sheet surface the reason with a retry action. Verification strictness is unchanged: an unverified library is never extracted or loaded, and a malformed recognized capability still fails Gateway validation (#337).
- **The engine loads from the archive.** `initBindings()` with no path only worked in a developer checkout, so a packaged Agent could never load sherpa. Engine libraries now ship inside the per-platform-tag runtime archive under `native/<tag>/sherpa/<library>` with the loader-relative paths the library appends, the daemon passes that directory to the worker, and Windows preloads `onnxruntime.dll` by path first. The archive contract grew one bounded shape, enforced by the Agent updater, the Client bootstrap installer, and both installers (#337).
- **Linux arm64 dictates through whisper only.** Flutter publishes no Linux arm64 host SDK, so that lane builds with the standalone Dart SDK and `sherpa_onnx`, which declares `environment: flutter`, cannot be compiled. The engine is a swappable local package instead: the arm64 lanes resolve a stub that exposes the same package name, library, and public names with `sherpaEngineAvailable = false`. That is a capability, not a failure — the catalog and the model rows are filtered, a stored sherpa selection falls back, `select` refuses with `model_unavailable`, and streaming and VAD are reported as absent. Both builds are unit-tested on one machine (#337).

## Installation and platforms

- **The Agent is published for Linux arm64.** `scripts/install.sh` already mapped `aarch64|arm64` to `arm64`, but the release matrix built only macOS arm64/x64, Linux x64, and Windows x64, so an Ubuntu 24.04 aarch64 host stopped at an artifact that did not exist. An `ubuntu-24.04-arm` lane now builds, smokes, and archives `sanad-agent-<v>-linux-arm64` with the same steps, `release-build` Environment, and trust policy as Linux x64, and `requiredAgentReleaseTargets` is the single declaration of the official Agent matrix that `validate-contract` and release preparation enforce, so a supported target cannot be dropped silently (#359).
- **A Linux root install resolves its own Home.** The systemd unit runs as the dedicated `sanad-agent` account, whose passwd `$HOME` is the Sanad Home, but `getSanadHome()` returned `$HOME/.sanad` when `SANAD_HOME` was unset. Every service command therefore looked in a second, empty Home and answered `Failed` or `Service exists without Sanad ownership metadata`, and it created that tree. The installed binary and unit now decide the Home before the account default, `service status`, `service stop`, and `service start` act on the real unit from any working directory and from a root shell whose `HOME` is `/root`, and `--home` still wins as the explicit override (#365).

## Daemon memory

- **A long-running daemon stays bounded.** A source daemon reaching a 2104 MB heap after about 22 hours had two independent causes. Four owners rebuilt the accumulated answer on every provider delta, so a 20 MB answer arriving in 4 KB deltas cost 25 seconds of copying and 176 MB of resident memory that the JIT heap kept permanently; content, thought, and reasoning now accumulate in `StringBuffer`s and the committed message is materialized once. The history snapshot cache was capped at eight sessions regardless of size and `PlatformRuntimeBridge` kept one response emitter per session forever — a closure that captures the Client socket, so every session the daemon had ever served pinned a closed `WebSocket`. The cache is now bounded by retained text (32 MiB) as well as by count, an identity check no longer materializes the payload, and a channel-scoped emitter is released with the channel that registered it while a reconnecting channel or the in-process CLI keeps its own (#369).

## Sessions, notices, and permissions

- **Every durable notice is readable, not only the live one.** The Client rendered a scheduled rate-limit retry while `sanad session show` answered `resuming` with `runtime_notice: null` and `retry: null`, `sanad session retry` refused the session as "not blocked or waiting", and a re-attached `sanad run` stayed silent about the wait. The Client was right by construction — it renders the live broadcast, while every other reader consumes the durable projection, and that projection dropped the notice. `session.query` now projects every non-`cleared` notice with the live wire vocabulary and with recovery actions widened so a scheduled wait is actionable, `retry_attempt` and `retry_budget` persist as additive nullable columns so `retrying (n/N)` and the retrying-versus-blocked decision survive a restart, a re-attached turn journals one `retrying (n/N)` record, and `session retry` classifies with the same `RuntimeRetryState.fromProjection` that `session show` uses (#372).
- **A run session keeps the mode it was created with.** A `session_created` projection of a first turn that carried only `--execution-root` or `--allow-all-tools` built its metadata from the registered workspace, so it had no `workspace_id`, no `execution_root`, and no `permission_mode`; a Client message into an existing run session omitted `allow_all_tools`, and the runtime orchestrator reset it to `false`; and changing the picker wrote to the workspace policy while the UI read "Default" and the Agent still auto-approved. Turn targeting now seeds the created session with its root, its `exec_root:` workspace identity, and its owner turn's authority; a turn that keeps its targeting inherits the session's durable authority while an explicit value stays authoritative and a retargeting turn revokes it; and the new `set_session_permission_mode` command writes the session's own override and republishes the full payload, which only an `owner` transport may raise to `full_access` (#351).
- **Deleting a session reaches every connected client.** `delete_session` produced exactly one `session_deleted` envelope stamped `DeliveryPolicy.origin`, which on the local transport resolves to the single socket bound to that session, so the CLI's own reply was the only delivery and a Flutter Client kept showing the conversation until it restarted. Deletion now also publishes through `GatewayManager.publishFamilyEvent` (#364).
- **A recovered session gets its own title.** After a daemon restart every recovered session logged a 404 model-not-found title failure and fell back to the user message, because title generation used the raw stored model id instead of the route the session actually resolves. Recovered titles now go through the session provider (#368).

## Secrets and startup

- **The daemon never waits on, and never prompts for, the OS credential vault.** A daemon opened the OS vault synchronously before it served anything and was allowed to start an OS authorization dialog, so on a Home whose items belong to another code identity the read either blocked inside the security framework or was refused immediately — with nothing listening and the same alarming block on every start. The daemon decision is now `forbidden` (`daemon_background`) on macOS Keychain, Linux Secret Service, and Windows DPAPI alike, the CLI entry opens no vault when it dispatches to a daemon, and the vault opens off the startup path: `beginOpen()` returns immediately in `opening` with a bounded, never-throwing `readyWithin`, a read or write while opening fails with the new `vault_not_ready` reason instead of reporting a value as absent, `/health` publishes `secret_vault: opening|available|unavailable`, and one WARNING line per start names what is unreadable plus the `sanad vault authorize` recovery route. An explicit user action is now the only path to a prompt (#370).

## Client

- **A new account can finish onboarding on a phone.** An account that signed in on a phone with no devices could not reach Settings, Profile, or Sign out, and `/settings?section=profile` fell back to General because the personal-section resolution lived inside a `targetDevice != null` guard; the post-create install page — and its creation-only pairing token — was replaced the moment the created device entered the inventory; the composer had no route into provider setup because the model chip was gated on a capability that stays false until a device reports a snapshot; and the wordmark and the add-device header overflowed a phone width. A `HomeShellScaffold` now owns the drawer, the drawer affordance, and the desktop-only status bar for both the Home and the zero-device surface, personal settings resolve without a device, the setup screen routes Home only while it is the live top route, the composer keeps its pickers visible whenever no request is pending, the provider gate is clamped to the viewport, and both headers scale down (#371).
- **The Client bundles no Apple font.** App Store validation rejected iOS build 22 with ITMS-91182 because the Client bundled Apple's SF Pro, which `flutter_sficon` carried as its only asset for a single glyph. The composer send arrow now draws `CupertinoIcons.arrow_up` at the same size and colour from Flutter's own icon font, `FloatingGlassButton` uses a standard `Icon`, and `flutter_sficon` is removed; a guard fails on a declared dependency, a resolved lock entry, an asset, or a built font manifest that carries an Apple font while still allowing `Cairo` and `CupertinoIcons` (#367).

## Developer tooling

- **`sanad-dev inventory` answers whether a worktree can be removed.** One read-only projection now carries bounded disk size per worktree, last-commit age, upstream state with ahead/behind, an opt-in cached `--pr` lookup, and one `safe`/`keep` verdict with the first blocking reason in operator order: primary checkout, missing, locked, detached, live runtime, Test Home, uncommitted changes, unpushed commits, gone upstream, unknown tracking. The JSON schema moved to 2 additively, and a new `cleanup-orphans` is dry-run by default, lists every target with `delete` or `refuse` and a named reason, and deletes only strictly inside `<primary home>/dev` with `--confirm`, refusing the primary Home, a Test Home, the dev area itself, a group directory, a symbolic link, and any live runtime (#363).
- **`sanad-dev ui` expresses five more behaviours.** Long press (`tap --hold-ms`), in-app hover (`hover --key`), an allowlisted extension call (`ext --name ext.sanad_client.<name>`), obscured-target reporting instead of a misleading `no_observable_change`, and tooltip text on keyed and actionable rows. Hover and long press run inside the Client's own pointer pipeline, so neither needs window focus or an accessibility grant, and a target covered by an overlay is reported with the blocker's bounds and nearest key rather than clicked (#366).
- **The Web Client stays signed in across Chrome restarts.** flutter_tools gives every launch a throwaway browser profile, and the Web Client keeps its Portal access and refresh pair, device id, and client instance id in `localStorage`, which browsers scope to the profile *and* the origin. A persistent profile per Test Home keeps all of them (#374).
- **A supervisor stall is measured from real progress.** The worker's progress clock advanced only on a `tool_use` timeline record, and a headless `sanad run` turn publishes only lifecycle records, so a task that worked for 70 minutes was reported silent at exactly its threshold while `status --brief` reported progress seconds old; `queued_stall` fired for every task merely waiting for a busy slot. Progress is now sampled from the task's timeline, stdout, stderr, and result artifact, `progress_resumed` reports the silence it ended, `queued_stall` is reserved for a real defect, and the daemon's stated retry deadline extends the silence clock so a scheduled retry is not a stall (#362, #372).
- **A continue attempt pins its session.** `continue --new-session` stripped `--session` so the CLI created a fresh daemon session, but the id that attempt opened was never written back, so every later plain `continue` opened yet another session and the operator saw a new conversation. The reported id is now recorded and appended as the task's pin, `status`, `status --brief`, and `inspect` name the continuation target, and a task that already pins a session is never rewritten (#373).

## CI and release

- **Stable releases are announced after Production, exactly once.** The Discord workflow subscribed to `release: published`, and `release.yml` publishes with the repository `GITHUB_TOKEN`, from which GitHub starts no workflow — so no announcement had fired since `v1.0.0-rc.1` and nothing could notice, because the absence of a notification is not a failure. The workflow now runs on the completing release run, refuses unless every serialized Production asset job succeeded in that same run, resolves only the Release that run itself published — never an RC, a validation-only dispatch, or a rejected approval — and records an announce-once ledger so a re-run cannot repeat a tag (#360).
- **Production is verified after every release, not only while we deploy it.** Every check inside the release and deployment workflows runs while it owns the deployment and appends a per-release marker, so a stale cache entry can never be observed. A separate read-only workflow now compares every version-bearing public surface with the newest published Stable release, reports an open release window instead of failing while that release is still a Draft, sends `Cache-Control: no-cache` with no marker and refuses a URL that carries one, and annotates each surface that is behind (#358).
- **A committed fixture can no longer block a Production deploy.** The private deploy archive check rejects any member whose final path component ends in `pem`, `key`, `p12`, `pfx`, `dump`, or `sql`, and three committed agent-state fixtures ended in `.sql`, so every private Production deploy was blocked. They are now `*.sql.txt` renames with no content change, and a guard fails on any tracked path with a rejected suffix while allowlisting only the embedded release verification key (#361).

This release was built from tagged public source by the protected Sanad release workflow. Verify downloads against `SHA256SUMS`, `release-manifest.json`, and GitHub build provenance before installation.

> [!WARNING]
> **Unsigned Windows build:** Sanad Agent and Sanad Client `1.0.22` artifacts for Windows x64 intentionally do not carry Authenticode signatures. Windows Defender or SmartScreen may show an unknown-publisher warning. Download only from this official `EastStarAI/sanad-agent` release, verify the manifest, file size, SHA-256, and GitHub provenance, and do not disable platform protection. Windows release gates run on Windows 11; Windows 10 has not been validated. The Client update package remains signed separately with WinSparkle DSA; that update signature is not Authenticode and does not establish a Windows publisher.

macOS and Android artifacts use their documented platform signatures. Linux and Windows artifacts are bound to the release through checksums, the immutable manifest, SBOM, and GitHub attestations.
